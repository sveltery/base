# Menu native registration enrollment diagnosis

Source confirms an unintended dependency opportunity in the native trigger attachment. The actual registration publication reads the Menu Store while running inside Svelte's attachment effect, then can publish to that same Store. The button host publication also reads reactive button state. A narrow native `untrack` boundary can remove those incidental dependencies while preserving the real registration owners and all Original business branches.

This is a source-only diagnosis and proposed repair. It is not SOURCE CLEAR, a demonstrated runtime root cause, an exact callback-count diagnosis, whole-family acceptance, or Main/merge approval.

A publisher stack does not establish that the Positioner or Popup attachment itself enrolled, and Popup's source specifically rules out its direct publication reads as a tracked attachment dependency. The feedback opportunity is concrete even without a later unrelated write. On an initially open Menu, adding a trigger can run `select('open')` before publishing the changed trigger count. The native attachment has then read the same subscriber version that the count publication increments. If that invalidates the attachment, its teardown removes the trigger and republishes the lower count; setup adds it and republishes the higher count. The log contains both removal (`popupStoreUtils:99`) and addition (`:106`) publication stacks. Source and these finite traces support the opportunity; they do not establish every scheduling step, a precise iteration count, an error name, or a complete runtime cause.

The native retained fixture genuinely uses `Menu.Root defaultOpen`, an actual `Menu.Trigger`, actual Portal/Positioner/Popup/Item, and a changing public `finalFocus`. Its business trigger is therefore relevant to the initially-open count path. The fixture/test assertions were only read, not modified.

## Smallest supported native primitive candidate

Use narrowly scoped native `untrack` at the **actual publication bodies**, with genuinely consumed owner inputs acquired before those boundaries:

1. In `useTriggerRegistration`, keep the current `const id = getId()` and `const store = getStore()` outside `untrack`. Run only the following Original registrationRef/triple comparison, captured-owner delete/add, map checks and `syncTriggerCount` body inside `untrack`. The captured store and ID remain actual native invalidation inputs, and the Original captured previous registration remains the cleanup owner. Keep all body order, no-op checks, count rules and undefined-ID behavior.
2. In `applyTriggerData`, capture its current Store and trigger ID before `untrack` and use those captured values in its unchanged imperative select/branch/update body. Continue reading the latest `stateUpdates` only in the same Original business branches inside that publication. The existing separate data-forwarding native effect still observes `isMountedByThisTrigger` and real `stateUpdates`; it is not suppressed. This keeps a payload change from becoming a registration-resource lifetime dependency.
3. In Trigger's actual host attachment, isolate the imperative `buttonRef(host)` invocation with `untrack`. The existing independent `useButton` `$effect(updateDisabled)` remains fully tracked and owns disabled changes. Host/ref order and direct native markup remain intact. Native effect teardown already disables reactive enrollment (`execute_effect_teardown` sets active reaction to null); a symmetric cleanup-call boundary may be explicit, but is not required to establish this setup-side finding.

These are three precise boundaries in the already used helper/caller bodies, with no new generic attachment adapter. The **current migration effect is a separate caller**: it already observes Store/ID before untracking publication. Its existing boundary protects that call only; it does not isolate the directly invoked attachment publication. Keep its genuine Store/ID migration and actual prior-owner cleanup.

This candidate leaves `SvelteStore.select` reactive, retains Source count/registry/data and Store mutation algorithms, and keeps the user's native independent attachment lifetime. It does not use a blanket untrack around attachment inputs, markup, getProps, native effects, or all Store reads; no fake cache, stable snapshot, tuple/Object.is dependency guard, React commit transport or ref/style custody is introduced. Existing reusable state-owner class requirements remain binding in any authored implementation; this bounded diagnosis does not certify current entire-closure role organization.

A count-only untrack would leave the data-application selected reads. A registration-only untrack would leave the button publication dependency. Removing registration/count publication or suppressing real ID/store invalidation would change Source business. Adding untrack to Popup solely because its setter appears in the stack would not be source-supported.
