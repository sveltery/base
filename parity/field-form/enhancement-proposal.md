# Proposed native remote submission boundary (decision pending)

Reference contracts are Base UI v1.8.0 commit `47b40521eab921c2756bf9bdb0b0f07fbfdb8c8c` and the actual fixture dependency SvelteKit `2.70.3`. Base Form validates synchronously in its submit listener, focuses the first invalid field, calls `preventDefault()` and returns before either consumer submit callback. It leaves subsequent native listeners and bubbling intact. Async validators do not hold submission pending. None of the accepted Input I-02/I-03/I-04 decisions changes this contract.

The secured [red run](https://github.com/sveltery/base/actions/runs/37063342115/job/111025003109) at `cfbe5eb867f498b57828911ff5acc1177f405a99` has 46 expected passes, one actual acceptance failure, zero skips and zero flakes. Verified artifact `11251439202` has ZIP SHA256 `984d850f822f5852cf8d80666def532e9fa4e06ff1fb6d098548fda1642fc9ac` and contains actual JSON/logs plus the failed acceptance error context and trace. Field invalidity caused one POST and a server counter delta of one (`6→7`) despite the consumer native callback being blocked. The independent invalid diagnostic measured `3→4`; native cancellation measured `4→5`; ordinary Form cancellation measured `5→6`. Kit's installed submit listener does not test preexisting `defaultPrevented` before preflight or its server operation, so the native cancellation probe also runs the operation. A green diagnostic means observations were recorded; it does not accept this outcome.

The proposed candidate keeps Base Form's validation timing and ordinary native submit behavior, and adds one automatic native boundary for **an invalid contextual Field on the actual native Kit remote form action**. It reads only the rendered `HTMLFormElement.method` and `action` URL. Kit `2.70.3` spreads an ordinary native POST action whose query contains `/remote`; no consumer adapter or new component prop is required. After the existing synchronous invalid verdict and `preventDefault()`, the candidate calls `stopImmediatePropagation()` for that native remote action. It does not wrap or inspect enhancement callbacks, attachment implementations, descriptor internals or DOM methods. It does not change valid submissions, ordinary actions, consolidation values, callback order or async submission rules.

This **changes propagation for invalid remote-action submits**: subsequent same-target listeners and bubbling observers do not receive the submit event. The URL convention is a version-scoped Kit interoperability assumption, not a browser standard or a guarantee for every enhancement library. Ordinary actions and consumer cancellation must keep pinned propagation. Replacement hosts must use their actual native form/action. Server validation failures must preserve zero operation delta, value/result/reset state and issue ownership. A request/operation delta acceptance case must stay red until this boundary demonstrably works; divergence earns no ordinary parity credit.

Alternatives considered:

- `preventDefault()` alone retains source propagation but the actual Kit operation still occurs; it fails the authorized requirement.
- Applying `stopImmediatePropagation()` to every invalid Form would alter ordinary source behavior and other integrations.
- Earlier capture/click/Enter validation would move the pinned validation boundary and cannot cover `requestSubmit()` uniformly without an additional propagation boundary or a DOM API patch.
- Setting native `noValidate=false` cannot stop a newly discovered custom error before native constraint checking, and changes the default native validation contract.
- Rewriting Kit enhancement attachments or requiring `.enhance(...)` consumer adapters violates the integration constraints and couples the component to opaque internals.

The candidate remains proposed and unaccepted until the PM reviews its concrete runtime diff and secured source/ordinary/remote propagation observations. It is not covered by the Input compatibility decisions. The final documentation and central differences register must record any approved decision before merge.

Native property hardening uses read-only `HTMLFormElement` prototype getter calls to brand the actual host and avoid named-control collisions with `method`, `action`, `target` or DOM methods. As in the installed Kit handler, submitter overrides are selected by attribute presence, then read through the native `HTMLButtonElement` or `HTMLInputElement` getter for `formMethod`, `formAction` and `formTarget`. Getter calls brand actual controls, including another document's controls. Native action properties already resolve relative URLs; an empty `formaction` uses the submitter's document URL even when a `<base>` supplies a different base URI. A synthetic DIV with override attributes cannot supply these native properties. Unavailable getters, malformed actions and non-form hosts safely fall through to ordinary pinned prevention and propagation. These reads never replace or patch a DOM API. JSDOM lacks `formMethod`/`formAction` getters and form named-property overrides: its method-override case establishes unavailable-getter fallthrough only, while actual property normalization and named-control behavior require the secured Chromium witnesses.

Kit `2.70.3` checks `target === '_blank'` literally even though native reserved browsing-context names are case-insensitive. The candidate currently follows that installed enhancement exclusion; `_BLANK` and `_Blank` are separate raw diagnostic executions against native and contextual forms, pending measured evidence and the scoped PM decision. No target-case compatibility acceptance is implied by diagnostic execution.

The focused review of `7451d68cd303ab709cdc7f4b2ebbd5ec2eab19c8` identified raw-attribute false positives for synthetic DIV submitters and empty `formaction` under a remote `<base>`, plus a false negative for an empty action on a remote document under an ordinary base. The corrected candidate adds seven secured acceptance supplements: a DIV override witness; both document/base combinations on the default and rendered Form; and actual button/input reflected method/action/target selection. Every case checks zero invalid POST/operation/reset, ordinary or suppressed later listeners as selected by the actual native properties, then a next valid one-POST/one-operation/one-reset path. These are supplemental proposed-boundary counterproofs, not ordinary upstream declaration ports or propagation-policy approval. Browser collection is 345 cases; secured execution and the scoped PM decision remain pending.
