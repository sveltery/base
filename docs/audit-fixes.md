## Dialog Portal target fidelity

Pinned [FloatingPortal](https://github.com/mui/base-ui/blob/47b40521eab921c2756bf9bdb0b0f07fbfdb8c8c/packages/react/src/floating-ui-react/components/FloatingPortal.tsx) recognizes native nodes before dereferencing an object ref. A ref with `current: null` uses the inherited Portal node or body fallback; an explicitly null container waits without creating a Portal. The [pre-change Svelte resolver](https://github.com/sveltery/base/blob/cdd1c4f3bef7d329b890de42c05aeb9d4402e656/packages/base/src/lib/dialog/Portal.svelte#L18) instead treated both values as the wait condition and could mistake an HTMLElement carrying a `current` property for a ref.

The repair recognizes HTMLElement/ShadowRoot targets with their owner document's Node constructor before reading `current`, then maps a null ref value to undefined fallback. This preserves explicit null waiting, inherited targeting, SSR omission, context forwarding, attachment ownership and teardown. Owner-document recognition also supports iframe targets without assuming the current realm's Node constructor. Optional-chain the owner document itself: a structurally valid ref may have an unrelated `ownerDocument: undefined` property and must still resolve its `current` target, matching the pinned native-node check. This boundary check is retained rather than removing validation based on types. This is a fidelity repair, not a correction of an upstream defect or a new native Svelte Portal primitive.

[DOM cases](../packages/base/tests/dom/dialog-portal-container.test.ts) cover undefined, explicit null, null ref, element, element with `current: null`, ShadowRoot and iframe targets plus cleanup, inherited nested fallback and live fallback/explicit-target changes. A ref with an unrelated undefined owner document is an additional boundary regression. The [paired browser suite](../tests/browser/dialog-portal-container.spec.ts) runs the same target scenarios against Svelte and the pinned React dependency. The audit's paired temporary runtime reproducer established the first two differences; permanent final-head browser execution remains a required gate. Inherited fallback coverage must be retained when changing this resolver.

## Initially undefined DOM refs

Pinned [useRenderElement](https://github.com/mui/base-ui/blob/47b40521eab921c2756bf9bdb0b0f07fbfdb8c8c/packages/react/src/internals/useRenderElement.tsx) forwards the actual rendered host with separate ref merging. Svelte uses bindable DOM props and attachments rather than React callback/object refs. The [pre-change Element](https://github.com/sveltery/base/blob/cdd1c4f3bef7d329b890de42c05aeb9d4402e656/packages/base/src/lib/dialog/Element.svelte#L5) and forwarding parts used `$bindable(null)`. Svelte accepts an unbound undefined value but throws `props_invalid_value` for an initially undefined bound prop with a fallback, even though the public optional ref type accepts undefined. A rendered audit test reproduced the error; this is documented Svelte fallback behavior, not a Svelte runtime bug. See [official bindable documentation](https://svelte.dev/docs/svelte/$bindable).

The approved adaptation removes the fallback with `$bindable()` consistently through Element, Button and the existing Dialog/Toast DOM-ref forwarding chains. Initially undefined and null refs both publish the actual host when attached and null on cleanup. An omitted or initially undefined ref can remain undefined before attachment, replacing the previous implicit null initialization. This is an intentional relaxation of the Svelte API; it does not claim React ref syntax equivalence. Imperative `actions` bindings, render-snippet attachment requirements and lifecycle cleanup remain unchanged.

[DOM regressions](../packages/base/tests/dom/ref-contract.test.ts) and [secured browser regressions](../tests/browser/ref-contract.spec.ts) cover the sixteen existing DOM-ref surfaces with both undefined and null initial values; Element, Button and Dialog.Trigger additionally exercise replacement-snippet hosts and teardown. Coverage is supplemental Svelte API evidence, not a port of shared React conformance. Existing SSR/package-consumer and lifecycle checks remain required. Pending [Portal PR #22](https://github.com/sveltery/base/pull/22), audited at `9699ab6b141f1ac29ecddeb8c7fdd65ff5a05b7f`, adds Toast.Portal and requires its own consistent ref adaptation and review after integrating the main fixes; it is not included in this main baseline.

## Viewport settlement cleanup

The [pre-change Viewport](https://github.com/sveltery/base/blob/cdd1c4f3bef7d329b890de42c05aeb9d4402e656/packages/base/src/lib/toast/Viewport.svelte#L67) called `settlePendingBlur()` twice consecutively in window keydown and blur handlers. The first call clears the pending item, so the adjacent second call has no work. Keep one call in each handler before its existing event handling. ## Typed native Toast contexts

Pinned [Provider context](https://github.com/mui/base-ui/blob/47b40521eab921c2756bf9bdb0b0f07fbfdb8c8c/packages/react/src/toast/provider/ToastProviderContext.ts) and [Root context](https://github.com/mui/base-ui/blob/47b40521eab921c2756bf9bdb0b0f07fbfdb8c8c/packages/react/src/toast/root/ToastRootContext.ts) provide per-tree state and reject missing required context. The pre-change Svelte [Provider helper](https://github.com/sveltery/base/blob/cdd1c4f3bef7d329b890de42c05aeb9d4402e656/packages/base/src/lib/toast/context.ts) and [Root helper](https://github.com/sveltery/base/blob/cdd1c4f3bef7d329b890de42c05aeb9d4402e656/packages/base/src/lib/toast/root-context.ts) manually managed keys and typed casts.

Native `createContext<T>()` supplies typed get/set/has functions. Check `has` before `get` to preserve the existing Base errors: `Base UI: getToastManager must be used within <Toast.Provider>.` and `Base UI: ToastRootContext is missing. Toast parts must be used within <Toast.Root>.` Keep per-Provider/Root isolation, stable live facades and context forwarding through imperative Portal mounts. This is a framework substitution without an intended observable behavior change.

Get/set are available since Svelte 5.40; the third `has` function requires **5.57.0**, as recorded in the [official release notes](https://svelte.dev/blog/whats-new-in-svelte-september-2026). Installed Svelte **5.57.1** and Base's peer range **`^5.57.1`** support the complete API without a version upgrade. The audit's temporary candidate passed 83 Toast DOM tests and one SSR test. The permanent [missing-context regression](../packages/base/tests/dom/toast-context.test.ts) retains the descriptive Provider error. Existing checks must retain Root errors, nested isolation, title/description registration, manager replacement/disposal and SSR isolation before claiming implementation acceptance.
